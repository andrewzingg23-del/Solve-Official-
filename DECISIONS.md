**2026-10-05 — $10,000 a person a year, with crypto at the core.** The founder: "this should be a $10,000 per person a year eventuality that this can make. Also needs to integrate crypto heavily."
- **How it is read (the founder can correct):** solve should eventually help each person make $10,000 a year through it. The north star becomes money made through solve per person per year, counted only from real outcomes and labeled by basis. solve earns a share when that money is real ("paid when it's real"); at a 10% share, that is $1,000 a person a year.
- **Crypto:** it follows the monetary constitution, which already makes the chain the truth for money and a witness for the record (Parts I, V and XV). It comes in stages:
  1. anchor the record on Solana, so receipts can be checked by anyone (no money);
  2. the person links a wallet they control (non-custodial);
  3. payments between people settle on chain and come back as `externally_verified` income;
  4. SOLVE, under Part XV's gates.
- **Gates that still hold:** no mainnet mint, custody or real money without the founder's explicit approval and legal review (constitution Part XV).
- **The $10,000 is ours:** a goal, not a promise shown to people. Earnings claims are regulated, so it is never advertised without substantiation.

**2026-10-03 — A model behind the boundary; consent stays the person's; contact authority is task-scoped.** Founder direction. Claude now interprets typed goals and suggests among the routes the Horizon computed, behind the existing reasoning-provider interface, using structured outputs and the server-side refusal fallback; forced tool use is not available on the default model, so the schema is the contract, and every reply is validated twice. **2026-10-03 — Kernel v4 is rehearsed on the store's Postgres major, shaped like the store.** Step 2 of the founder's path. A Supabase staging branch could not be created (two attempts timed out; none appeared), and this build container cannot reach `*.supabase.co`, so the staging copy is a local Postgres 17.10 server configured as the store is (non-superuser `postgres` owning the kernel and running migrations; API roles through a non-inheriting `authenticator`), rebuilt from the three applied migrations and proven identical to the live kernel by fingerprints read from the store. The embedded test kernel is Postgres 18 running as superuser, and the difference mattered: deferred constraint triggers run as the session role on 17 and as the queuing role on 18, so every ledger posting by an API caller would have failed at commit on the store. v4 runs those trigger functions as their owner. `npm run test:postgres` keeps the whole suite runnable on 17 with real concurrent connections, which also exposed a stale-read race in the settlement worker (fixed). What only the store can prove (Auth email and redirect, Data API exposure, real token claims, the schema cache) is listed in `docs/plans/2026-10-03-kernel-v4-rollout.md` with the live runbook, which waits for the founder's go-ahead.

**2026-10-03 — The answer service is woken by delivery and trusts only the kernel.** Step 1 of the founder's path to one real agent task. An organization's agent runs as its own process with its own session; a wake carries no content, and every pass reads the agent's inbox and the kernel's reply links, so a restarted service needs no local state. There is no kernel push channel to another process yet: a deployed service watches its own inbox (one read per interval) and the sandbox rings an in-process doorbell; a contentless kernel notification is the later improvement once v4 runs live. Two fixes came out of the failure tests: a step whose proposal reply was lost is continued rather than proposed again (re-proposing with terms re-derived from a moved World was refused by the kernel as a different request and would have retried forever), and a kernel error while reading the inbox now fails the pass instead of reading as an empty inbox. An agent's steps in the exchange loop now run through the agent's own session, never a separately constructed one.

**2026-10-03 — The counterparty's side is a transition, not a responder.** The sandbox answered inquiries with a function that read an agent's inbox and replied; the real other side is a principal running the same loop. A delivered inquiry is now a fact of the recipient's World (observed, with the asker's provenance), answered when the kernel's reply link shows a completed reply; `inquiry.answer` is a native transition whose payload is the organization's published record; the agent derives one goal per open inquiry, plans it through its own Horizon, records the selection in its own scope and replies under its own authority in the market, addressed to the asker and bound to the inquiry. Arcadia's counterparties now run exactly this (`lib/causal/exchange.ts`), so the browser sandbox exercises the two-sided loop rather than a shortcut. Transitions may name a target actor and a message they answer; v4 `read_actions` exposes `in_reply_to` so the answered state is read from the kernel, not inferred from payloads.

**2026-10-03 — The other side acts when it acts; providers ask and look, never assume.** Arcadia's counterparties answered inside the provider call, which hid the real shape of the world: the organization you ask is somewhere else and answers later, if at all. Providers are now idempotent per action and re-performable: a run that finds no answer leaves the step `needs_reconciliation` with nothing canonical, and the next run asks again under the same key, so one action asks one question however many times it runs. The kernel-messaging providers are the real ones (the counterparty agent replies from its own session under its own authority; a verifier attaches its own finding), and Arcadia's are those same providers with the other side also running on this device. An HTTP counterparty reaches an organization that is not on SOLVE through the endpoint its record publishes (never one named in a payload; TLS unless loopback), with the same `Idempotency-Key` on every run and the answer hashed into the evidence. Routes, decisions and consequences are identical across all three; only history's `provider` differs. Email was not built: without a real transport in this environment it would be another simulation.

**2026-10-03 — Plans belong to their maker; organizations act through delegated agents.** Route selections are recorded in the selector's own actor scope, not the World's: a plan is interpretation attributable to whoever made it, while the World's history holds consequences. Since a spawned agent holds no authority over its own scope (its creator does), an agent keeps its own plans only when its creator delegates reading and recording there, which is recorded and revocable. Arcadia/8 makes organization owners market members who delegate reading, verification requests and planning to their agents, so an organization's agent can pursue its organization's goal end to end with no human in the loop and no second code path, and is refused what it was never given (sub-agents, commitments, grants to itself).
**2026-10-03 — Money moves as a transition, not a feature.** A good-faith deposit to the agreed supplier runs through the same registry, planner, pipeline, guards and reconciliation as every other transition; the only new code is a provider wrapping the existing payment router and a `pays` relation kind. The amount travels on the action, so the kernel's leases decide budgets (a companion leased $20 is refused $25, with the reason). A lost chain reply leaves the action attempted and the World unchanged although the money moved; the next run reconciles from the chain marker and the consequence lands once. The browser sandbox has no chain, and its Horizon says so rather than pretending: "blocked: no provider for payment.send is connected".
**2026-10-03 — Transitions are declared, not coded; guards are the kernel's.** The planner no longer knows the supply domain. Transitions declare what they require, produce, change and guard, over patterns of facts; the Horizon chains them backward from desired facts, and any World can extend the registry. Two goal kinds (secure supply, verify a claim) run through the same planner, pipeline and providers. Guards moved into the kernel ("only if this still holds"): judged at proposal, re-checked before enactment, and turning a lapsed outside effect into reconciliation. A step's concrete terms are fixed at proposal from the current World, not at planning time: the agreement carries the quote that was recorded, not the one predicted. Verification in Arcadia is the market's own service (Kestrel) attaching externally verified evidence to the claim unless its audit challenged it; a claim's status moves asserted → verified by evidence, never by assertion.
**2026-10-03 — One causal loop; consequences declared by actions.** The car-company flow had bespoke code for each step (ask, delegate, accept, and a separate relation write after acceptance). It now runs through one primitive in `lib/causal`: Horizon plans routes from World state for the acting principal; a selected route is recorded; every step goes through one pipeline; the kernel applies each action's declared consequences in the same transaction that completes it (kernel v4: `validate_consequences`, `apply_consequences`). Providers are evidence sources, not truth; routes name capabilities, not providers. Planning is interpretation: route rankings are versioned policies, selections record the policy they were made under, and planning never writes. An assisting companion receives recorded grants to see the World and the market and to record findings, but contacts and commits only through delegation or its principal.

**2026-10-03 — Kernel ids are per generation; identity across generations is the natural key.** Making Arcadia's kernel ids identical across generations was attempted and rejected: Postgres dispatches the built-in `gen_random_uuid` by OID to its C implementation (redefining it in `pg_catalog` has no effect), kernel functions pin `search_path = ''`, and the applied migrations that mint ids cannot be edited. The strongest invariant kept: same seed → same semantic digest and same JS-side keys and ids; `arcadia_key` names the same thing across generations; within a generation one id serves kernel, snapshot, browser and renderer. Timestamps and the hash chain that commits to them are the remaining intentional differences.
**2026-10-03 — Arcadia is reproducible and its snapshot is a projection.** Arcadia is SOV's permanent synthetic civilization, not a fixture. A seed fixes every key and id its generator creates; a semantic digest of the whole kernel (ids, keys, signatures and timestamps replaced by order of first appearance) is identical for the same seed, generator and kernel, and the manifest records generator, seed, configuration, kernel, policies, digest and counts. The browser snapshot is the kernel's own database: the build reloads it and refuses to publish unless it reproduces the digest, and the browser reproduces it again at boot (`npm run test:world`). Kernel row ids still differ per generation; `arcadia_key` attributes and digest labels identify the same thing across generations.

**2026-10-03 — Rendering is replaceable and geography is never invented.** CesiumJS sits behind a SceneController contract; the product speaks in semantic camera operations and spatial view models, and only `app/world/cesium-scene.ts` touches Cesium. The venture World used to be placed at the average of its suppliers' coordinates (labelled "estimated"); it now has no location and is listed off Earth, so its route lights the real suppliers instead of drawing lines from a fictional point. A refused contact is now proposed and recorded (a rejected action) rather than checked silently, so the World can show it; acceptance writes an agreement relation to the World Graph, so the World changes because of the consequence.

**2026-10-03 — Private records stay private at every read path.** Review found that `read_events` returned the creation event (title, location, attributes) of entities `read_world` hides. v4 withholds events, evidence and action payloads that would disclose a private record, by the same rule as `read_world`. In the sandbox the whole synthetic database lives in the visitor's browser by design; for real data the kernel runs on the store and these rules decide what leaves it.
**2026-10-03 — SOV operates SOV on its own primitives.** The first self-operation loop (a payment whose chain response was lost) uses tasks, leases, governed actions and verification exactly as users do; nothing is a special path. Roles follow least power: the payment service's code detects and its agent works the task (only the payment service can read the payer's wallet address); a separate trust service's agent verifies, so worker and verifier are distinct parties; the payment service performs the write only for an action the kernel authorized and re-checks the chain itself. Agents attach observations as `artifact` evidence: the kernel's rule that only service actors claim `system_observed` or `externally_verified` stays, because an agent's observation is a record it produced, while the chain confirmation comes from the service. The first build proposal from repeated friction is recorded with a computed Class A; building and promoting it is the next, separately gated loop.

**2026-10-03 — Limited leases authorize only where their limits are checked.** Review of v4 found that the v1 grant lookup ignored lease limits, so every earlier function gated by a capability alone (`record_payment`, `read_events`, settlement) would have treated a lease limited to one task, amount or counterparty as unlimited. v4 now hides limited leases from that lookup, adds `find_permitted_grant` (limits checked against the request; used for task transitions and approvals, so verifier leases can be limited to one task) and `find_delegable_grant` (sub-leasing within limits keeps working), and ends task-limited authority when the task closes. v4 is still unapplied, so this lands in the same migration.
**2026-10-03 — Authority, not humanness, controls action.** The authority engine decides from grants, lease limits and policy: ALLOW, REQUIRE_SECOND_AUTHORITY, REQUIRE_QUORUM, REQUIRE_MULTISIG, REQUIRE_DELAY, REQUIRE_CHALLENGE_WINDOW, DENY. Nothing checks whether the actor is human. Agents enact, create agents and hold leases; no principal expands its own authority outside a grant or governance process. Source: founder's agent-enactment correction. Kernel v4.

**2026-10-03 — One action physics.** Every consequential operation is an action with one lifecycle (proposed → authorized → enacting → completed | failed | needs_reconciliation; rejected; cancelled). Settlements and payments keep their proven tables and map onto it. Kernel-native kinds enact atomically; external kinds record `enacting` before the outside call and complete with evidence.

**2026-10-03 — One gate for direct writes.** `issue_grant`, `record_event` and `post_transaction` now pass the same policy decision as actions (redefined in v4 with only that change). A governed capability cannot be exercised directly; it must go through an action.

**2026-10-03 — The sandbox kernel runs in the browser.** With email sign-in off, the World runs on the real kernel in the visitor's browser (PGlite, persisted to IndexedDB), seeded from an Arcadia snapshot generated by the real kernel, chain and router code. PGlite's own files are served untouched from `/public/pglite` and imported natively; bundling it under Turbopack breaks its WASM loader. The database boundary lives in `lib/sandbox/pglite.ts` and can move to a Worker, Webpack or server Postgres without touching kernel semantics. The exact kernel test files pass in Chromium (`npm run test:browser`).

**2026-10-03 — Email sign-in off for now.** Founder request. Enter opens the app directly. `/login` and `/account` remain, unlinked; the live store is untouched by the sandbox.

**2026-10-03 — Payments route without forcing SOLVE.** Routes are ranked only by cost in the denomination; quotes keep spot, TWAP, executable amounts, depth and timestamps; venues co-sign only after verifying their own flows. Test assets only.
